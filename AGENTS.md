# Rewards Tracker for YNAB

A client-side rewards tracker with a Next.js web app and an Expo mobile app. Both analyse YNAB transactions to track credit card rewards with user-defined rules, and share the rewards engine, storage types and utilities in `packages/app-core`. User data lives in browser or device storage; there is no application database and there must be no server-side dependency. `packages/db` is unused.

## Architecture contracts

- Web persists through the `storage.ts` service (browser `localStorage`); never access `localStorage` directly. Mobile mirrors this through AsyncStorage, with the PAT in SecureStore.
- Web calls YNAB through the `/api/ynab/*` proxy (bearer PAT); mobile calls YNAB directly.
- Cloud Sync is optional and stores client-encrypted payloads in Cloudflare KV. The Agent API (`/api/agent/rewards`, docs at `/agent-api`) is stateless: it decrypts Cloud Sync data in memory per request and recomputes rewards.
- The PAT is never included in exports or backups.
- All cards are YNAB-linked; do not reintroduce manual cards.
- Check each platform's implementation before assuming feature parity with the web app.
- Bump `STORAGE_VERSION` in the app-core storage constants only when a deliberate cross-platform reset is required.

## Rewards and units

- All amounts are milliunits internally (YNAB standard).
- Raw rewards: cashback in dollars, miles in miles. Normalise everything to dollars before comparing; never mix reward units.
- Eligible spend is the amount between the minimum and maximum spend that earns rewards.
- Block-based miles ("1 mile per $5") apply per transaction, not on total sums.
- Period labels are `YYYY-MM` (calendar month) or `YYYY-MM-DD` (billing cycle).
- Use "dollars" in identifiers (not "USD"). The UI shows `$` but never hardcodes currency symbols or values.

## Conventions

- British spelling in user-facing copy, US spelling in code identifiers.
- Feature flags live in `packages/app-core/src/config/featureFlags.ts`, the source of truth for available flags. Toggling needs a rebuild. Flagged implementation files stay intact with a header comment noting the flag, and their routes stay reachable by direct URL for testing even when hidden from navigation.
- Raster app icons are generated by `node scripts/generate-icons.mjs`, never hand-edited; the master vector and brand guidelines are in `design/brand/`. Use the in-app `BrandIcons` components over generic lucide icons for brand moments. Brand gold is the `--spark` token (`text-spark`); brand crimson is `--primary`.
- Follow the user's request and the checked-in code for current work. Do not manage work from repository-local task databases unless the user asks. Keep this file to durable architecture and conventions, not status snapshots or TODO lists.

## Checks

- `pnpm lint` and `pnpm typecheck` cover the web app and shared packages; `pnpm mobile:typecheck` covers mobile; `pnpm test` lints and runs the primary test suites.

## Deployment

- The web app runs on Cloudflare Workers via OpenNext at https://rewards.soon.sg. Production normally deploys by pushing to `main` and monitoring the `Deploy to Cloudflare Workers` workflow.
- Use the manual deploy (`pnpm --filter ./apps/web deploy:cloudflare`) only when a local deploy is specifically required. OpenNext skew protection also needs `CF_WORKER_NAME`, `CF_WORKERS_SCRIPTS_API_TOKEN` and `CF_ACCOUNT_ID` as configured in the deploy workflow; a successful `wrangler whoami` is not sufficient if the token cannot read Worker versions.
- Inspect the current Expo/EAS configuration before changing mobile release workflows.

## Mobile UI

- Keep iOS information hierarchy quiet and native: navigation titles name the current object or destination, and screen content must not repeat them.
- Do not decorate routine facts with dots, pills, badges, colours, uppercase eyebrows or success labels. Normal states such as connected, active, linked, tracking, earning and up to date should usually be silent; reserve emphasis for actions, decisions, warnings, errors and exceptional states.
- Prefer deleting redundant copy or controls over restyling them. Pull-to-refresh owns routine refresh, native navigation owns dismissal, and one clear content action owns a form commit.
- Make the Overview forward-looking: prioritise which cards can still earn and their strongest factual use over prominent earned-value totals. Omit cards whose current-cycle cap is already reached; Cards and card detail remain the complete portfolio record.
- Preserve meaningful data encodings such as YNAB flag colours and threshold/cap progress. Review optical alignment on a simulator rather than assuming a technically centred custom navigation view will look native.
